## § 0 The question (READ)

`tests/test_p12_severity_sign.py::test_which_paranoia_level_catches_the_simulated_revert`
pins that a regression of the 2026-08-09 I14 fix (simulated by no-op'ing
`src/zanzibar/graphindex/wildcard.py::WildcardIndex._ensure_entity_middles`) serves a
fail-OPEN answer at `off` AND at `residue`; only `full`/`fixpoint` abort. `CLAUDE.md` and
the `src/zanzibar/graphindex/invariants.py` module docstring recommend `residue` for
production. So the recommended production tier is blind to a regression whose severity is
an authorization over-grant. Engineering call, model decides (`CLAUDE.md` "Who decides").

## § 1 Scouting (READ, 2026-10-12)

* **I14 is vacuous on plain OpenFGA schemas.** It ranges over
  `src/zanzibar/schema/rules.py::SchemaInfo.crossable_shapes` = `bridged_in_shapes &
  bridged_out_shapes`. Bridged-out shapes come only from object wildcards (`folder:*`),
  which have no DSL syntax and already warn `UnprovenExtensionWarning`; the docstring says
  plain `[user:*]` usage "is never crossable". So for every schema without
  `object_wildcard_shapes`, an I14 tier costs nothing if it returns on an empty
  `crossable_shapes`.
* **Today's I14 is a whole-store scan.** It lives inside
  `invariants.py::check_invariants`, which loads every `Node` and `Edge` of the store
  (`_load`). The `residue` tier's contract (`check_residue_hygiene` docstring) is "does NOT
  grow with store size", so moving the existing clause into it verbatim would break that
  contract.
* **Every `Node` write goes through the ORM.** grep of `src/zanzibar/graphindex/*.py` for
  `insert(` / `update(` finds bulk inserts of `Edge`, `Residue`, `ResidueRef`,
  `DeltaOutbox` only (`bulk_build.py`, `core.py::...insert(DeltaOutbox)`); node creation,
  refcount changes and deletion are `session.add` / `session.delete`
  (`core.py` refcount paths ~:950-:975, dated 2026-10-12). So an `after_flush` listener sees
  every node an entity's I14 status can depend on.
* **What an entity's I14 status depends on** (REASONED from the clause text): the entity's
  concrete nodes (existence, `implicit`, `reference_count` -- the "bridge-only middle"
  test), the two wildcard nodes of each crossable shape, and the two bridge edges per
  middle. Bridge add/remove moves the endpoints' `reference_count`, so it dirties the
  middle node. A wildcard node's refcount moves on EVERY bridge add, so wildcard nodes
  must trigger a re-scan only on create/delete, or every write would scan the whole type.

## § 2 Decision (REASONED)

**Add a DELTA-SCOPED I14 to the `residue` tier**, rather than only documenting the gap:

1. The defect class is a fail-OPEN, and `residue` is sold as "the security-relevant tier".
   Documenting that it misses one would leave the recommended production setting blind to
   a known over-grant regression.
2. The cost is zero on every schema without crossable shapes (early return; the listener
   is not even installed), and O(entities touched by the transaction) otherwise -- the
   same order as the write itself, so the tier still does not grow with store size.
3. Clause code is SHARED with the full checker (one `_check_i14_entities` both call), the
   same rule ZT-P1-3 set for I6, so the tiers cannot drift.

Scope boundary, stated honestly: the delta is the set of `(type, name)` entities with a
`Node` row created, modified or deleted in the transaction, plus a whole-type re-scan when
a crossable shape's wildcard node is created or deleted. A bridge `Edge` row removed
WITHOUT its endpoints' refcounts moving is I13 corruption, which stays outside `residue`
(`tests/test_paranoia_wiring.py::test_tier_boundary_is_what_it_says_it_is`).

### § 3.2 Cost (MEASURED 2026-10-12b)

`benchmarks/probe_tk118_residue_i14.py 160 480`: interleaved arms, min-of-3, per-write
commits through `ConnectedStore`. `residue-pre` is residue with the TK118 listener and check
patched to no-ops. This run predates the `_crossable_types` cache, so it is pessimistic for
the I14 arm. Literal output:

```
plain  160 writes: off   7.643s | residue-pre   9.073s (+18.7%) | residue   9.053s (+18.4%) | I14 share  -0.2%
plain  480 writes: off  19.367s | residue-pre  20.031s ( +3.4%) | residue  20.800s ( +7.4%) | I14 share  +3.8%
owc    160 writes: off   6.768s | residue-pre   7.752s (+14.5%) | residue   8.681s (+28.3%) | I14 share +12.0%
owc    480 writes: off  33.907s | residue-pre  39.741s (+17.2%) | residue  41.994s (+23.8%) | I14 share  +5.7%
```

Reading (REASONED):
* **plain:** I14 is vacuous there by construction, so the `-0.2%` / `+3.8%` spread is this
  instrument's noise floor. It is large: `residue-pre` alone reads +18.7% at 160 and +3.4%
  at 480.
* **owc:** the I14 share FALLS as the store grows (+12.0% at 160, +5.7% at 480). That is
  consistent with O(touched entities) and not with O(store). A store-proportional check
  would rise, as `full` does (+124% to +303% in the 2026-07-26 measurement).
* The `residue` tier itself read +14% to +19% over `off` at 160 writes here. The
  2026-07-26 figures in `tests/test_paranoia_wiring.py` are +4.3% / +5.7%, measured on a
  different fixture and machine state. With a noise floor this wide, that gap is not
  evidence of a regression. UNVERIFIED either way.

### § 3.3 Verdict

The decision in § 2 stands. The cost is zero where I14 is vacuous (every schema without
object wildcards), and on a crossable schema it is a single-digit-to-low-double-digit share
that shrinks with store size. That is a fair price for the recommended production tier no
longer serving a known fail-OPEN regression.
