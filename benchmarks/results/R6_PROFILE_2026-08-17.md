# R6 motivating-measurement pass — 2026-08-17

**What this is.** `docs/perf-round6-audit-2026-08.md` filed 18 code-verified but
**unmeasured** candidates. `docs/perf-next-round.md`'s reopening rule says each one owes
a motivating measurement before it is worth landing — the audit confirms the code *does*
the inefficient thing, not that the inefficiency *dominates*. This is that pass for the
six read-path candidates (`R6-1` … `R6-6`). **Nothing was implemented and nothing landed.**

**Instrument:** `benchmarks/profile_r6.py` (added with this pass) — cProfile plus counters
keyed to each candidate's own claim, over the reviewed `scale_bench` datasets. Deterministic,
no RNG. Box: 12 logical cores, idle — the user stopped the three background processes from
another repo before the runs, and CPU-delta sampling confirmed 0 CPU-seconds/6 s on each
beforehand. Wall-clock is therefore usable, not just the counters.

**Two honest limits on every number below.**
1. **In-memory SQLite.** A round trip is microseconds and there is no network. This
   *understates* `R6-6` (whose win is one PostgreSQL RTT per eliminated statement — the
   statement COUNT is the transferable metric) and *overstates* ORM cost relative to real
   I/O. Statement counts and call counts transfer; seconds do not.
2. **Under cProfile** absolute throughput is depressed several-fold. Ratios and shares are
   the signal; the unprofiled sweep in §1 is the honest throughput.

**Scope: ALL EIGHTEEN are now measured.** Sections 2–6 cover the read paths
(`R6-1` … `R6-6`, instrument `benchmarks/profile_r6.py`); sections 7–12 cover the write,
cascade, bulk and space candidates (`R6-7` … `R6-18`, instrument
`benchmarks/profile_r6_write.py`, added the same day). `R6-17` needed no run of its own —
it is a duplicate of `R6-3`, found independently by two agents, and is settled by `R6-3`'s
result. **Nothing was implemented for any of them.**

## 1. Unprofiled scaling sweep — the surface that actually degrades

`scale_bench --workload gdrive --backend set` (roaring), throughput per surface:

| scale | raw tuples | check /s | lookup /s | lookup_reverse /s |
|---|---|---|---|---|
| 200 | 3,360 | 32,301 | 570.7 | 7,167 |
| 400 | 6,720 | 29,981 | 573.8 | 7,225 |
| 800 | 13,440 | 30,640 | 254.3 | 2,616 |
| 1600 | 26,880 | 10,899 | 226.0 | 3,005 |

**`lookup` is 50–130× slower per call than `check` and degrades ~2.5× from scale 400 to
1600 while `check` stays flat until 1600.** That is the shape `R6-1` predicts, and it is
why the set-engine half of this pass focused there. (`scale_bench`'s own docstring already
predicted the asymmetry — the set engine's `lookup` is a full-store candidate sweep — so
this measurement confirms a documented design consequence, not a surprise.)

## 2. `R6-1` — lookup re-runs `check` with a fresh memo per candidate → **MOTIVATED**

`profile_r6 --target set-lookup --scale 800 --calls 150` (13,440 tuples, 11,040 interned keys):

```
results returned      : 9,311
wall (profiled)       : 1.52 s   (98.8 lookups/s under profiler)
SetEngine.check calls : 11,111  (74.1 per lookup)
...cumulative time    : 1.39 s  ( 91.4% of lookup)
_drive invocations    : 11,111  (1.00 per check)
```

**74.1 `check` calls per `lookup`, and 91.4% of lookup wall time is inside them.** The
precondition for the finding is met about as strongly as it can be: essentially all of
`lookup`'s cost is the per-candidate confirmation loop, and each call gets a fresh
`memo`/`inst_memo` (engine.py:1051-1052).

⚠ **What this does NOT establish, stated plainly:** that a shared memo would *eliminate*
that time. The profile proves `check` dominates; it does not measure how much of the work
across those 74 calls is *redundant*. Sizing the actual win needs a prototype of the
two-tier memo from the verifier's correction (naive sharing is a **correctness bug** —
see the audit entry, cycle-tainted roots must stay call-local). Recommendation: build the
prototype behind the measurement, do not land from this number alone.

## 3. `R6-2` — expand's left-folded `ms.union` → **NOT MOTIVATED on measured workloads**

`profile_r6 --target set-expand --scale 800 --expands 120` (gdrive `lookup_reverse`):

```
members returned      : 2,657
wall (profiled)       : 0.04 s   (2,937 reverses/s under profiler)
ms.union calls        : 2,520   (21.0 per call)
_starpop calls        : 7,560   (63.0 per call = 3 per union, as the audit predicts)
_normalize / _ext     : 2,520 / 5,040
MemberSet algebra self: 0.010 s  ( 24.2% of the surface)
```

The cost *structure* the finding describes is exactly present — 3 `_starpop` per `union`,
folded per element. But:

* the algebra is **24.2%** of a surface that is already **13–30× faster per call than
  `lookup`**, so the whole available win is a quarter of a non-bottleneck;
* the feared **quadratic star-population re-materialization did not appear** — with roaring
  ops `_starpop` measured ~1 µs/call even on a 20,000-user population;
* and `R6-2` **changes a modeled algorithm** (CORRESPONDENCE.md maps `MemberSet.union`,
  `expandDirect`/`expandTtu`/`expandStep`), so it costs a Lean model update + full phased
  gate + fuzz.

**Recommend DECLINE** on the round-5 precedent (a plausible candidate declined on a fresh
profile), unless someone first builds a workload combining a large star population *with* a
deep stored-TTU-parent fold and shows the quadratic term biting. Reopening means meeting
that measurement.

⚠ **Instrument correction, recorded because the first verdict was wrong.** The first version
of this probe used `set_engine_bench`'s wide/star schema (`viewer: public but not blocked`)
and printed `R6-2 NOT MOTIVATED, 18.8%` — with **`members returned: 0`** and only **240
unions for 120 expands**. On that schema `viewer` is star-CLOSED, so the answer lives in
`stars`/`neg`, `.pos` is empty by construction, and `direct_expand` folds a bitmap leaf in
ONE union: the per-element fold the finding is about **never ran**. A probe that exercises
nothing reports a clean verdict — the house failure mode, one level down from the checks
`docs/sabotage-procedure.md` covers. The right-answer-by-luck reading ("not motivated" was
also the final verdict) is exactly why this is written down rather than quietly fixed: the
second run reaches the same conclusion **for a reason the first run had not measured**.

## 5. `R6-4` / `R6-5` — the boolean graph read path → **BOTH MOTIVATED**

`profile_r6 --target graph-lookup --graph-scale 40 --calls 60` (demorgans_law_2, 980 raw
tuples, **100 residue rows**):

```
wall (profiled)       : 0.92 s   (65.5 lookups/s under profiler)
_collect_residue_...  : 60 calls, 0.275 s cum  ( 30.1%)      <- R6-4
json.loads calls      : 11,580  (193.0 per lookup)           <- R6-4
lookup_reachable      : 105 calls, 0.207 s cum  ( 22.6%)     <- R6-5
_classify_ids         : 105 calls, 0.271 s cum  ( 29.6%)     <- R6-5
_load_nodes           : 105 calls, 0.257 s cum  ( 28.0%)     <- R6-5
```

and the profile's single largest block is ORM row construction:

```
22410  0.083 tottime  0.298 cumtime  sqlalchemy/orm/loading.py:1068(_instance)
```

* **`R6-4`: 30.1% of every boolean lookup, and 193 `json.loads` per lookup over only 100
  residue rows.** The scan is O(#derived objects) with no filter beyond `store_id`, so this

* **`R6-5`: 22,410 ORM instances built (32.7% of profiled time) to read 3–4 columns.**
  `lookup_reachable` + `_classify_ids` together are 52% of the surface. This is the largest
  single measured block in the whole pass, and per the audit it is an **unmodeled** surface
  (CORRESPONDENCE §7.3), so it needs no Lean change — but it is netted only by the
  lookup-oracle suite, the matrix and fuzz, which is where its gate cost lands.

## 6. `R6-6` — `check`'s node resolution → **MOTIVATED, and the cheapest of the six**

`profile_r6 --target graph-check --graph-scale 150 --checks 1500` (gdrive, 2,520 tuples):

```
checks         : 1,500  (825 true)  in 3.81 s (394/s)
SQL statements : 7,125  (4.75 per check)
    node_v4      6,000  (4.00 per check)
    edge_v4      1,125  (0.75 per check)
```

**Exactly 4.00 `node_v4` point SELECTs per check**, against 0.75 for the already-batched
edge probe. The proposed fix batches the four identity resolutions into one, taking the op
from **4.75 → 1.75 statements, a 63% cut in round trips per check** — on the hottest read
surface in the system, on the supported server where each statement is one network RTT.
No Lean model change (the probe-key set is unchanged; keep the nested `check.key` closure
so the CORRESPONDENCE anchor still resolves).

# Part 2 — write, cascade, bulk and space (`R6-7` … `R6-18`)

Instrument: `benchmarks/profile_r6_write.py`. One framing fact bounds two of these before
any number is read: **`R6-7` and `R6-8` execute only at `PARANOIA_FULL`.** Production
defaults to `off`, the recommended tier is `residue`, and benchmarks disable paranoia
outright — so their entire ceiling is **gate/test wall-clock**, not production latency.
`PARANOIA_FULL` *is* the `tests/` default via `make_wildcard_index`, and the gate is tiled
around a 10-minute cap, so that ceiling is real money; it is just not the kind the audit's
"high" rating implied. Both were downgraded on this ground by the audit's own verifier.

## 7. `R6-7` / `R6-8` — the paranoia tier → **BOTH MOTIVATED, gate-only**

`profile_r6_write --target paranoia --scale 20 --commit-every 1` (336 raw tuples,
paranoia FULL, one commit per tuple):

```
outbox rows at end    : 1,556
check_invariants      : 674 calls, 23.72 s cum  ( 64.1%)
_check_outbox_sanity  : 674 calls,  7.66 s cum  ( 20.7%)   <- R6-7
verify_outbox_deltas  : 337 calls,  4.06 s cum  ( 11.0%)   <- R6-8
```

and the measurement that actually decides `R6-7` — **the growth curve**, run unprofiled so
cProfile's per-call overhead cannot manufacture the trend:

```
commits           : 336
first quartile    :   8.92 ms/commit
last  quartile    : 126.07 ms/commit
growth ratio      :  14.14x
```

**Per-commit cost rose 14× over 336 commits.** A share alone could not have distinguished
"expensive constant" from "grows without bound"; the quartile comparison does, and it
confirms the O(N²)-over-a-run claim directly. The outbox is append-only and `prune_outbox`
is never auto-called, so nothing bounds this but the run length. `check_invariants` as a
whole is **64.1%** of a paranoid build — the two candidates are half of that.

`R6-8` at 11.0% is real but secondary, and its own verifier's correction stands: the fix
must test membership against BFS *neighbours*, not the pre-seeded seen-set, or a `(s,s)`
pair reads reachable on corrupt state — which is the one state a corruption verifier exists
for.

## 8. `R6-9` / `R6-16` — the non-boolean write path → **BOTH MOTIVATED**

`profile_r6_write --target graph-write --scale 150` (gdrive, 2,520 raw tuples, **no derived
relations** — `ruleset.compiled.plans` is empty):

```
SQL statements        : 87,252  (34.62 per raw write)
    node_v4             43,683  (17.33 per write)
    edge_v4             39,324  (15.60 per write)
_db_node point SELECTs: 11,370  ( 4.51 per write,  17.7% of build)   <- R6-9
edge_v4 rows          : 14,868
OUTBOX rows emitted   : 14,868                                        <- R6-16
    -> outbox rows per closure edge: 1.00
```

* **`R6-9`: 4.51 point SELECTs per raw write, 17.7% of build time.**
* **`R6-16` is the clearest waste in the whole round: exactly 1.00 outbox row per closure
  edge on a schema that compiles no derived predicates at all.** 14,868 rows written,
  permanently retained (manual prune only), consumed by no cascade — because there is no
  cascade. This is simultaneously a write cost and an unbounded space cost.
  ⚠ It is also the most dangerous fix in the round, and the audit says why: **paranoia FULL
  uses the outbox as its worklist on ALL schemas**, so gating emission without gating that
  consumer would silently blind the checker. Design it against `R6-7`/`R6-8`, not
  separately — the same rows are involved.

Context worth carrying: **34.62 SQL statements per raw write.** On the supported server
that is 34 round trips per user-visible write, and the read-side `R6-6` finding (4.75 per
`check`) is small beside it.

## 9. `R6-10` / `R6-11` / `R6-12` — the incremental cascade → **two motivated, one not**

`profile_r6_write --target cascade --bool-scale 30 --incr 30` — bootstrap unprofiled, then
30 **incremental write + `run_cascade` + commit** cycles, the path
`tests/test_matrix.py::GraphBackend.apply` uses:

```
_stored_tupleset_subj : 16,690 calls, 26.38 s cum  ( 59.8%)   <- R6-10
_residue_cache_scope  : 240 entries                            <- R6-11
reconcile_subject     : 30 calls over 30 distinct keys SUMMED PER CASCADE
                        (1.00x intra-run; worst single cascade 1 call)   <- R6-12
```

* **`R6-10` is the largest single measured cost anywhere in round 6: 59.8% of incremental
  boolean write time** in one function, re-enumerating stored tupleset/userset tuples via
  SQL per candidate. Memoize at the `_stored_tupleset_subjects` level only, per its verdict.
* **`R6-11`: 240 cache scopes for 30 reconciles — the residue cache is built and torn down
  8× per reconcile.** The digest calls this a one-line scoping change with invalidation
  already in place; it is the cheapest item in part 2.
* **`R6-12` is NOT motivated: 1.00× intra-run re-reconcile, worst cascade one call.** A
  fan-out write that bumps many keys at once might exercise it; nothing in the reviewed
  workloads does. It needs a workload before it needs a patch.

⚠ **Instrument correction #2, same class as `R6-2`'s.** The first cascade probe profiled
`build_graph`, which bootstraps derived state through `DeltaProcessor.backfill()` — the
OFFLINE path. `reconcile_subject` was called **0 times**, and the probe confidently
reported `R6-11`/`R6-12` INCONCLUSIVE against a run that never executed the code they
describe. **Instrument correction #3:** the `R6-12` counter then aggregated calls across
all 30 cycles and printed "15.00× re-reconcile" — which is the same key touched by
successive *writes*, not the intra-run duplication `_bumped` is about. Per-cascade counting
gives 1.00×. Both corrections changed a verdict; neither was caught by anything but
re-reading what the number could mean.

## 10. `R6-13` / `R6-14` / `R6-15` — the bulk path → **none motivated**

`profile_r6_write --target bulk --bool-scale 300` — 32,550 tuples through the REAL bulk
path (`connectedstore.build_index(..., bulk=True)`; `_harness.build_graph` never reaches
`bulk_build`/`bulk_backfill`, so it would have measured nothing):

```
wall                   : 18.03 s
bulk _instances_of_type:       0 calls,  0.00 s  (  0.0%)   <- R6-13
bulk _stored_tupleset  : 221,460 calls,  0.90 s  (  5.0%)   <- R6-14
bulk _topo_order       :       1 call,   0.158 s (  0.9%)   <- R6-15
_reconcile_subject_edge: 145,560 calls,  4.55 s  ( 25.3%)   (context)
```

* **`R6-15` is refuted by upper bound: the entire topo sort is 0.9% of a bulk build.** A
  perfect heapq frontier cannot win more than that. Decline.
* **`R6-14`: 5.0% ceiling** across 221,460 calls — the calls are numerous but individually
  cheap. Below the threshold that justifies touching the bulk path.
* **`R6-13` is UNREACHED** — 0 calls, though the bulk path plainly ran (its functions
  dominate the profile). It is the bulk twin of `R6-3` and needs the same star/wildcard
  shapes to fire. Two independent findings, both unreachable by any benchmarked workload.
* Where bulk time actually goes: `_reconcile_subject_edge` at **25.3%**. That is not any
  filed candidate — if the bulk path is ever worth optimizing, this is where to look, and
  it should be filed as a new id rather than smuggled into one of these.

## 12. `R6-18` — EdgeV4 physical layout → **MOTIVATED, 53.1%**

`profile_r6_write --target space --rows 200000`. The claim is about a physical layout, not
about this project's logic, so it can be measured exactly without touching production
models: build both layouts in real file-backed SQLite, insert identical rows, `VACUUM`,
compare bytes.

```
A: surrogate PK + unique index :  11,538,432 bytes  (57.7 B/row)
B: WITHOUT ROWID composite PK  :   5,406,720 bytes  (27.0 B/row)
saved                          :   6,131,712 bytes  (53.1%)
```

**The closure table is 2.1× larger than it needs to be**, and `EdgeV4` is the biggest table
in the system (the materialized transitive closure). This is the ceiling of the fix; the
real change also owes a hand migration for persistent PostgreSQL, since there is no alembic.

## Recommended order (measured, not filed)

**Land, in this order:**

1. **`R6-10`** — 59.8% of incremental boolean write time in one function. The largest
   measured cost in the round. Memoize at `_stored_tupleset_subjects` only.
2. **`R6-6`** — 4.75 → 1.75 statements per `check`; smallest blast radius, no Lean change.
3. **`R6-11`** — one-line scoping change; the cache is torn down 8× per reconcile.
4. **`R6-5`** — 32.7% ORM construction to read 3–4 columns; unmodeled surface.
5. **`R6-4`** — 30.1% of boolean lookup, and grows with store size.
6. **`R6-9`** — 4.51 point SELECTs per write, 17.7% of a non-boolean build.
7. **`R6-18`** — 53.1% off the biggest table; needs a hand migration for persistent PG.
8. **`R6-16`** — 1.00 unconsumed outbox row per closure edge, but **co-design with
   `R6-7`/`R6-8`**: paranoia FULL reads those rows as its worklist.
9. **`R6-7`** (+ `R6-8`) — gate wall-clock only, but 14× per-commit growth makes it the
   one term that gets worse every time the suite grows.
10. **`R6-1`** — largest read ceiling (91.4%) but prototype the two-tier memo first; the
    naive fix is a correctness bug.

**Decline / defer, with the number that says why:**

| id | why not |
|---|---|
| `R6-15` | entire topo sort is **0.9%** of a bulk build — that is the whole ceiling |
| `R6-12` | **1.00×** intra-run re-reconcile; worst cascade one call |
| `R6-14` | **5.0%** ceiling across 221k cheap calls |
| `R6-2` | **24%** of a non-bottleneck, at the price of a Lean model change + fuzz |
| `R6-3` / `R6-17` / `R6-13` | **0 calls** — three findings (two independent) on branches no benchmarked workload reaches |

**How the measurement moved the audit's own ranking.** The digest put `R6-6`,
`R6-11`, `R6-12`, `R6-9` in "quick wins" and `R6-1`, `R6-4`, `R6-10` in "the big three".
Measurement **confirms** `R6-6`/`R6-4`/`R6-10` (and makes `R6-10` the headline), **promotes**
`R6-5` (filed medium, measured as the largest read block) and `R6-16` (filed high on
reasoning, now with 1.00 rows/edge behind it), and **demotes five**: `R6-2` (filed high),
`R6-12` (a quick win that wins nothing here), `R6-14`, `R6-15`, and the `R6-3`/`R6-13`/`R6-17`
family. That is five items of implementation effort the round would otherwise have spent,
and it is the reopening rule paying for itself.

**One unfiled finding.** `bulk_backfill._reconcile_subject_edge` is **25.3%** of a bulk
build and belongs to no candidate. It should get its own id rather than be folded into one
of these; this pass did not investigate it.
